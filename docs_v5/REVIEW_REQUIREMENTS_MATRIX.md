**仍然不支持的**（如实披露）：
- 没有多人协作、权限和指派；“联系发布方”需要线下进行。
- 没有附件上传，证据只能以文字登记。
- 再检测会另存为一条新记录，通过编号关联，而不是在同一条记录里对比修改前后。
- 文案建议是程序模板，不是模型针对具体情况生成的。

## B. 法律规则审查意见（LEGAL_RULE_AUDIT）逐项回应
| 审查项 | 当前实现（证据） | 结论或局限 |
|---|---|---|
| 性别限制 | `reason=explicit_sex` 映射为 flag（`rfl/contract_v2.py` 中的 `REASON_TRIAGE`）。冻结的 `REASON_SOURCES[explicit_sex]` 为 S01、S02、S03、S04，**没有区分限男和限女** | 局限：冻结映射会对限女的情况同样列出 S01。复核卡已经分支写明“限女不机械援引第43条第1项”。是否修改冻结映射，需要法学方决定后另立版本 |
| 婚育 | 婚育条件统一为 `marriage_birth`，对应 S01、S02，**没有区分**限制结婚、生育计划、婚育状态、询问和孕检 | 局限：冻结的分类只有一类。复核卡写出了第43条第2、3、4项的区分，并要求审核人判断属于哪一类 |
| 照护 | `care_condition`（布尔值）和 `sex_link` 是两个独立字段；照护条件映射为 review；界面文案不推断性别；评估中单列“照护被推断为性别”的错误 | 满足 |
| 岗位能力 | Prompt 写明工作安排和能力要求本身不是线索；开发集上正常条件的误报为 0/7（这是开发集结果） | 满足（仅开发集证据） |
| 角色声部 | 后处理 v2.3 的范围检查：角色或声部的表述没有同时限定应聘者身份时，从 flag 降为 review，不会直接判为 clear；没有行业豁免 | 满足，但这是规则兜底，模型本身仍会误报 |
| 例外 | `exception_missing` 映射为 unknown；unknown 也会保留已经发现的条件片段（finding 不会被丢弃） | 满足。规范名称、条款和事实字段由人工在复核卡中填写 |
| 语境 | 线索按条件逐条提取；有 scope 字段；一句平等声明不能覆盖其他条件 | 满足 |
| 文档汇总 | flag > unknown > review > clear，属于冻结版本的**界面优先级**，所有线索都保留 | 需要法学方在测试前确认；目前沿用冻结版本，并已在评分协议 v1.1 第 8 条中写明 |
| 法源细化到条和项 | 冻结的 `source_ids` 只到法律文件这一级，**没有细化到条和项，也不含 S21** | **局限，已披露**。条款级参考只在复核卡里提供，不参与评分，也不改冻结映射 |
| 失败处理 | JSON 失败、证据不在原文、空输出都计为 invalid，**不会被当作 clear**；所有原始输出和失败都保存；重试规则已在评分协议中预先固定 | 满足 |

需要法学方确认的两点：
1. 是否接受冻结的法源映射保持法律文件级、在报告中如实披露？
2. 文档汇总优先级是否认可？

如果要修改其中任何一项，必须在测试前重新冻结，并另立版本。

## C. 规则表、版本与哈希（供法学方核对）
- `REASON_TRIAGE`：explicit_sex 和 marriage_birth 对应 flag；care_condition 和 context 对应 review；exception_missing 对应 unknown。没有线索时为 clear；scope 为 insufficient 时为 unknown。
- `REASON_SOURCES`：explicit_sex 对应 S01、S02、S03、S04；marriage_birth 对应 S01、S02；care_condition 对应 S02、S04、S07、S08；context 对应 S02、S04；exception_missing 对应 S01、S05。
- 线索类型的枚举：explicit_sex、marriage_birth、care_condition、context、exception_missing；scope 的枚举：recruitment、context_only、training、insufficient；sex_link 的枚举：explicit、suggested、unestablished、none、unknown。
- 文件哈希见 `docs_v5/LOCKED_TEST_FREEZE_RECORD.md`。

## 达到的条件
- 契约、证据子串、分母处理都由程序检查。invalid 不会被改判为 clear。
- review、unknown 能够表达不确定性，上一轮这一项是 No-Go 的主要原因。
- 照护条件没有被推断为性别：0/7。引用、历史、否定语境的误报：0/18。
- 多条件并存能分别列出 finding，注入指令没有被执行。

## 没达到 / 风险
1. **角色/声部全部误报**（4/4）。即使规则里写了开发集原话也没修好。
   - 建议的处理：界面上对含“角色”“饰演”“声部”的 finding 显示“可能为角色或声部描述，请人工确认”。如果加程序后处理规则，要作为 v2.2 单独记录版本，并在锁定测试前冻结。
2. **键名拼写错误**：`missing_facts` 被写成 `missing_fs`、`missing_fotes`，导致 1–2/86 条无效。可选方案：
   - 改键名，例如 `facts_needed`（这需要改提示词）。
   - 或做受控的别名映射。但别名映射属于“修补模型输出”，与“不修补”的原则冲突，需要负责人决定。
3. 欢迎性表述仍有误报（E033）。
4. **延迟**：单条约 20–30 秒。内存紧张时首条可能要几十分钟，Demo 现场需要先预热、关闭其他大程序。批量推理延迟尚未测。
5. **标签**：全部是 AI 辅助意见或工程探针。规则与标签的一致率不等于法律准确率。
